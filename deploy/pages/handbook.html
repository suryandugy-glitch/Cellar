Start with a mental model.

The guidance below is published here directly; no external source browser is required to understand the workflow.

01 / What is a contract?

It is a machine-readable statement of what a consumer expects from an exported CSV: column names, formats, uniqueness, and row constraints. A producer can generate a valid file that is still incompatible with a consumer.

02 / How checking works

  1. Choose a consumer contract.
  2. Inspect the proposed CSV export.
  3. Compare its schema and values with expectations.
  4. Read failures and proposed remediation.
  5. Stop release if a breaking change remains.

03 / Read a verdict

PASS means the supplied sample satisfied the checked rules. FAIL identifies a broken expectation. Triage may suggest a rename, but it is a hypothesis to confirm before changing production data.

04 / Try the demo

Use the browser-based synthetic examples to see successful and failing checks. They demonstrate behavior; they do not represent a production customer environment.

Open sample walkthrough →

05 / Run locally

The full Java 21 application is run from its project workspace. Depending on the environment, use the provided launcher. Avoid entering sensitive customer CSV data into any public sample form.

./run.sh
# Windows: run.bat

06 / Architecture boundary

The public pages are a documentation/demo surface. The Java app and any backend connector have separate runtime and deployment requirements. A client-side sample does not imply a hosted production API is available.

Generate on pull requests

Export representative CSV data from the proposed code changes before running the Java checker.

Block breaking changes

Use the nonzero exit code to stop a breaking change, then inspect the affected consumer and suggested fix.

Collaboration

Clear ownership. Open ideas.

Cellar Studio is led by Suryandu Ganguly (Founder & CTO). Engineering work is separated into scoped areas so people can contribute without needing company-wide administrative access.

Software engineering

Own a bounded feature, tests and developer instructions for one scoped project.

Research & verification

Own an experiment, benchmark, reproducible bug or validation plan.

Design & documentation

Own navigation, accessibility, interactions, examples and clear explanations.

Security and access: product contributors should receive only the permissions needed for their work. Internal credentials, account administration, and confidential documents are not published on this website. Public examples and informational content are not a guarantee of service availability.
